# 视频直播 APP 注册/登录功能需求 Spec（后端首版）

## 1. 文档信息

- 文档主题：视频直播 APP 注册/登录功能
- 文档范围：后端接口与鉴权规则
- 文档日期：2026-04-20
- 适用阶段：V1 首版

## 2. 背景与目标

视频直播 APP 需要提供一套稳定、低门槛、适合移动端的账号接入能力，用于支持用户快速完成身份校验并进入业务场景。首版目标不是构建完整账号中心，而是优先打通最核心的手机号登录闭环，在尽量少的交互步骤下完成用户接入和登录态管理。

本次 V1 采用“手机号 + 短信验证码”作为唯一登录入口，并在验证码校验成功后自动完成注册或登录，无需将“注册”和“登录”分成两条用户主流程。服务端需要为 App 提供验证码发送、自动注册登录、Token 刷新、退出登录、登录态校验等基础能力，同时为后续扩展密码登录、设备管理、风控、第三方登录等能力预留清晰边界。

## 3. 产品决策结论

本次需求已经确认以下关键决策：

- 首版仅做后端接口与鉴权规则，不包含客户端页面设计。
- 首版主登录方式为 `手机号 + 短信验证码`。
- 用户输入验证码后，未注册手机号自动注册并登录。
- 登录态采用 `Access Token + Refresh Token` 双 Token 方案。
- 同一账号允许多设备同时在线，不因新设备登录挤掉旧设备。
- 密码登录、第三方登录、复杂风控等能力不进入首版交付范围。

## 4. 范围定义

### 4.1 In Scope

本次需求范围包括：

- 发送登录短信验证码
- 通过短信验证码完成登录
- 验证码通过后自动注册新账号
- 签发 Access Token 和 Refresh Token
- 刷新 Access Token
- 当前设备退出登录
- 获取当前登录用户基础信息
- 基础账号状态校验
- 基础限流、防刷、防重复提交能力
- 认证相关日志与审计字段

### 4.2 Out of Scope

本次不包含以下内容：

- 密码注册、密码登录、修改密码、找回密码
- 第三方登录（微信、Apple、QQ 等）
- 手机号换绑
- 图形验证码
- 登录通知、异地登录提醒
- 复杂设备指纹系统
- 风险评分模型、黑白名单系统
- 全设备下线
- 账号注销完整流程
- 用户资料完善流程
- 账号合并

## 5. 角色与使用场景

### 5.1 角色

- App 未登录用户：需要获取验证码并完成登录
- App 已登录用户：需要在 Token 过期前后保持登录态
- 运营/后台管理员：可通过账号状态控制用户是否允许登录
- 短信服务提供方：负责验证码下发

### 5.2 典型场景

#### 场景 A：未注册手机号首次进入

1. 用户输入手机号并请求验证码
2. 服务端发送验证码
3. 用户输入验证码并提交登录
4. 服务端校验验证码通过
5. 服务端发现账号不存在
6. 服务端自动创建用户账号
7. 服务端签发 Token 并返回登录成功

#### 场景 B：已注册用户再次登录

1. 用户输入手机号并请求验证码
2. 服务端发送验证码
3. 用户输入验证码并提交登录
4. 服务端校验验证码通过
5. 服务端发现账号已存在且状态正常
6. 服务端直接签发 Token 并返回登录成功

#### 场景 C：登录态续期

1. Access Token 过期或即将过期
2. 客户端使用 Refresh Token 请求刷新
3. 服务端校验 Refresh Token 合法
4. 服务端生成新的 Access Token，并建议轮换新的 Refresh Token

#### 场景 D：用户退出登录

1. 用户在当前设备主动退出
2. 服务端将当前会话置为失效
3. 当前设备后续刷新 Token 失败

## 6. 核心业务规则

### 6.1 身份与账号规则

- 手机号是首版账号唯一身份标识。
- 首版仅支持中国大陆手机号格式校验。
- 首版不区分“注册接口”和“登录接口”的产品主语义，统一通过验证码登录接口进入。
- 同一手机号最多绑定一个账号。
- 验证码校验通过后，如果手机号未注册，则自动注册。
- 自动注册时仅创建最小账号信息，不强制填写昵称、头像、性别等资料。
- 账号创建成功后立即进入登录成功态。

### 6.2 验证码规则

- 验证码仅可用于 `LOGIN` 场景。
- 验证码应为短时有效的一次性凭证。
- 验证码默认 6 位数字。
- 验证码有效期建议为 5 分钟。
- 验证码成功使用后必须立即失效。
- 同一手机号新验证码下发后，旧验证码可设计为立即失效，避免并行码混淆。
- 服务端不得通过验证码发送接口暴露手机号是否已注册。

### 6.3 登录态规则

- Access Token 用于访问业务接口。
- Refresh Token 用于续签 Access Token。
- Access Token 与 Refresh Token 必须分离。
- 同一账号允许多设备同时持有有效会话。
- 每次成功登录都应创建独立登录会话。
- 每个登录会话都应可关联设备信息。
- 当前设备退出登录仅使当前会话失效，不影响其他设备在线状态。
- Refresh Token 刷新成功后建议轮换生成新 Refresh Token，并立即作废旧 Refresh Token。

### 6.4 账号状态规则

账号建议包含以下状态：

- `ACTIVE`：正常，可登录
- `DISABLED`：已禁用，不可登录
- `BANNED`：已封禁，不可登录
- `DELETED`：逻辑删除，不可登录

规则如下：

- 账号状态校验发生在验证码校验通过之后、Token 签发之前。
- 非 `ACTIVE` 状态账号必须拒绝登录。
- 拒绝登录时不可暴露过多内部原因，客户端返回统一业务错误文案即可，详细原因记录服务端日志。

## 7. 业务流程设计

### 7.1 发送验证码流程

1. 客户端提交手机号和业务场景
2. 服务端校验参数合法性
3. 服务端执行手机号维度与 IP 维度限流
4. 生成验证码并持久化记录
5. 调用短信供应商发送验证码
6. 记录发送结果与请求追踪信息
7. 返回发送成功响应

注意事项：

- 不返回“用户是否存在”
- 不返回验证码内容
- 若短信通道异常，返回可重试错误码

### 7.2 验证码登录/自动注册流程

1. 客户端提交手机号、验证码、设备信息
2. 服务端校验参数格式
3. 服务端校验验证码是否存在、是否匹配、是否过期、是否已使用
4. 服务端校验登录尝试次数与防刷规则
5. 查询手机号对应账号
6. 若账号不存在，则创建用户信息和账号记录
7. 若账号存在，则校验账号状态
8. 创建登录会话
9. 生成 Access Token 与 Refresh Token
10. 返回用户信息和 Token 信息

### 7.3 刷新 Token 流程

1. 客户端提交 Refresh Token
2. 服务端解析并校验 Token 签名和格式
3. 查询会话是否存在、是否失效、是否过期
4. 校验 Token 版本或唯一标识是否匹配当前有效会话
5. 签发新 Access Token
6. 如采用轮换策略，则签发新 Refresh Token 并作废旧 Refresh Token
7. 返回新的 Token 信息

### 7.4 退出登录流程

1. 客户端携带 Access Token 调用退出接口
2. 服务端识别当前会话
3. 将当前会话状态置为失效
4. 使当前会话关联的 Refresh Token 不再可用
5. 返回退出成功

### 7.5 获取当前用户信息流程

1. 客户端携带 Access Token 请求当前用户信息
2. 服务端完成鉴权
3. 根据 Token 中用户标识查询用户基础信息
4. 返回用户基础资料和账号状态

## 8. 接口设计

统一约定：

- API 前缀建议使用 `/api/v1/auth`
- 所有接口返回统一 JSON 包装结构
- 成功时 `code = 0`
- 失败时返回业务错误码和可展示文案
- 所有涉及手机号、验证码、Token 的日志都必须脱敏

### 8.1 发送验证码

`POST /api/v1/auth/sms/send`

#### 请求体

```json
{
  "mobile": "13800138000",
  "scene": "LOGIN"
}
```

#### 字段说明

- `mobile`：手机号，必填
- `scene`：业务场景，必填，首版固定为 `LOGIN`

#### 成功响应

```json
{
  "code": 0,
  "message": "OK",
  "data": {
    "requestId": "sms_req_20260420_xxx",
    "expireInSeconds": 300
  }
}
```

#### 失败场景

- 手机号格式错误
- 发送过于频繁
- 当日发送次数超限
- IP 发送过于频繁
- 短信服务异常

### 8.2 短信验证码登录/自动注册

`POST /api/v1/auth/login/sms`

#### 请求体

```json
{
  "mobile": "13800138000",
  "smsCode": "123456",
  "deviceInfo": {
    "deviceId": "uuid-xxx",
    "deviceType": "IOS",
    "appVersion": "1.0.0",
    "osVersion": "17.0",
    "userAgent": "app/1.0.0",
    "clientIp": "203.0.113.10"
  }
}
```

#### 字段说明

- `mobile`：手机号，必填
- `smsCode`：验证码，必填
- `deviceInfo.deviceId`：设备唯一标识，建议必传
- `deviceInfo.deviceType`：设备类型，取值建议 `IOS` / `ANDROID`
- `deviceInfo.appVersion`：App 版本，建议必传
- `deviceInfo.osVersion`：系统版本，可选
- `deviceInfo.userAgent`：客户端标识，可选
- `deviceInfo.clientIp`：建议由服务端网关注入，不依赖客户端直传

#### 成功响应

```json
{
  "code": 0,
  "message": "OK",
  "data": {
    "isNewUser": true,
    "user": {
      "userId": 10001,
      "mobile": "13800138000",
      "nickname": null,
      "avatar": null,
      "status": "ACTIVE"
    },
    "token": {
      "accessToken": "access_xxx",
      "refreshToken": "refresh_xxx",
      "tokenType": "Bearer",
      "accessTokenExpireInSeconds": 7200,
      "refreshTokenExpireInSeconds": 2592000
    }
  }
}
```

#### 失败场景

- 参数缺失
- 手机号格式错误
- 验证码错误
- 验证码已过期
- 验证码已使用
- 验证码尝试次数过多
- 账号被禁用或封禁
- 系统内部错误

### 8.3 刷新 Token

`POST /api/v1/auth/token/refresh`

#### 请求体

```json
{
  "refreshToken": "refresh_xxx"
}
```

#### 成功响应

```json
{
  "code": 0,
  "message": "OK",
  "data": {
    "accessToken": "access_new_xxx",
    "refreshToken": "refresh_new_xxx",
    "tokenType": "Bearer",
    "accessTokenExpireInSeconds": 7200,
    "refreshTokenExpireInSeconds": 2592000
  }
}
```

#### 失败场景

- Refresh Token 缺失
- Refresh Token 非法
- Refresh Token 已过期
- Refresh Token 已失效
- 会话不存在

### 8.4 退出登录

`POST /api/v1/auth/logout`

#### 请求头

```http
Authorization: Bearer <access_token>
```

#### 成功响应

```json
{
  "code": 0,
  "message": "OK",
  "data": null
}
```

#### 说明

- 幂等处理
- 已失效会话再次登出可返回成功

### 8.5 获取当前登录用户

`GET /api/v1/auth/me`

#### 请求头

```http
Authorization: Bearer <access_token>
```

#### 成功响应

```json
{
  "code": 0,
  "message": "OK",
  "data": {
    "userId": 10001,
    "mobile": "13800138000",
    "nickname": null,
    "avatar": null,
    "status": "ACTIVE"
  }
}
```

## 9. 数据模型设计

以下为建议的数据实体划分，供后端设计时参考。最终字段可在详细设计阶段微调，但实体边界建议保持稳定。

### 9.1 用户表 `user`

建议字段：

- `id`：主键
- `mobile`：手机号，唯一索引
- `nickname`：昵称，可空
- `avatar`：头像 URL，可空
- `status`：账号状态
- `created_at`
- `updated_at`

设计原则：

- 首版以 `mobile` 作为唯一账号标识
- 不将密码字段放入首版主表设计必需项
- 预留扩展字段空间，但首版不强制落库过多资料

### 9.2 验证码记录表 `sms_code_record`

建议字段：

- `id`
- `mobile`
- `scene`
- `code_hash`
- `status`：`INIT` / `SENT` / `USED` / `EXPIRED` / `FAILED`
- `provider`
- `request_id`
- `expire_at`
- `used_at`
- `send_ip`
- `attempt_count`
- `created_at`
- `updated_at`

设计原则：

- 不明文存储验证码，建议存储哈希值
- 支持追踪短信发送结果
- 支持记录验证码校验尝试次数

### 9.3 登录会话表 `auth_session`

建议字段：

- `id`
- `user_id`
- `session_id`
- `refresh_token_hash`
- `device_id`
- `device_type`
- `app_version`
- `os_version`
- `login_ip`
- `status`：`ACTIVE` / `LOGGED_OUT` / `EXPIRED` / `REVOKED`
- `last_refresh_at`
- `expire_at`
- `created_at`
- `updated_at`

设计原则：

- 一个设备一次登录对应一个会话
- 多设备登录通过多条会话记录实现
- 服务端应能根据会话状态控制 Refresh Token 是否继续可用

### 9.4 登录审计表 `auth_login_audit`（可选）

建议字段：

- `id`
- `user_id`
- `mobile`
- `result`
- `reason_code`
- `device_id`
- `device_type`
- `client_ip`
- `created_at`

用途：

- 用于登录成功/失败审计
- 支撑安全排查与运营统计

## 10. Token 设计建议

### 10.1 Access Token

建议包含：

- `userId`
- `sessionId`
- `tokenType=ACCESS`
- `issuedAt`
- `expireAt`

建议：

- 采用 JWT 或等价的签名 Token 方案
- 有效期建议 2 小时
- 不建议过长，降低泄露风险

### 10.2 Refresh Token

建议包含：

- `userId`
- `sessionId`
- `tokenType=REFRESH`
- `issuedAt`
- `expireAt`
- `jti` 或类似唯一标识

建议：

- 有效期建议 30 天
- 服务端保留会话记录并校验 Refresh Token 状态
- 首版采用轮换策略，降低重放风险

### 10.3 鉴权拦截规则

- 业务接口默认校验 Access Token
- 刷新接口仅接受 Refresh Token
- Access Token 解析后需校验用户状态
- Access Token 即使未过期，若账号状态已变为不可用，也应拒绝继续访问

## 11. 安全与风控要求

首版不做复杂风控，但必须具备基础安全能力。

### 11.1 限流要求

建议默认值：

- 同一手机号 60 秒内最多发送 1 次验证码
- 同一手机号每日最多发送 10 至 20 次验证码
- 同一 IP 每小时发送次数需有限制
- 同一手机号验证码校验连续失败达到阈值后，进行短时锁定

### 11.2 防枚举要求

- 发送验证码接口不得暴露手机号是否注册
- 登录失败文案应尽量统一，不区分“用户不存在”和“验证码错误”
- 日志中手机号需脱敏展示

### 11.3 防重放要求

- 验证码只能使用一次
- Refresh Token 轮换后旧 Token 必须失效
- 同一 Refresh Token 重复使用时应识别为异常或直接拒绝

### 11.4 数据安全要求

- 验证码不明文存储
- Token 不明文落库，建议存储哈希值
- 手机号在日志、监控、审计中需脱敏
- 密钥和短信渠道配置必须存放在安全配置中心或环境变量中

### 11.5 审计要求

- 记录验证码发送结果
- 记录登录成功/失败结果
- 记录 Token 刷新结果
- 记录登出动作

## 12. 错误码设计建议

建议定义统一错误码体系，以下为示例：

| 错误码 | 含义 |
| --- | --- |
| `AUTH_001` | 参数错误 |
| `AUTH_002` | 手机号格式错误 |
| `AUTH_003` | 验证码错误 |
| `AUTH_004` | 验证码已过期 |
| `AUTH_005` | 验证码已使用 |
| `AUTH_006` | 验证码发送过于频繁 |
| `AUTH_007` | 验证码发送次数超限 |
| `AUTH_008` | 登录尝试次数过多 |
| `AUTH_009` | 账号状态异常，禁止登录 |
| `AUTH_010` | Access Token 无效 |
| `AUTH_011` | Refresh Token 无效 |
| `AUTH_012` | Refresh Token 已过期 |
| `AUTH_013` | 会话不存在或已失效 |
| `AUTH_014` | 短信服务异常 |
| `AUTH_999` | 系统内部错误 |

要求：

- 错误码稳定，不随文案变化
- 客户端根据错误码决定交互分支
- 文案与错误码分离，支持后续国际化

## 13. 非功能需求

### 13.1 性能要求

- 验证码发送接口应在正常情况下快速响应，不因短信供应商慢响应长时间阻塞主线程
- 登录接口在验证码已命中的情况下应保证稳定低延迟
- 刷新 Token 接口应支持高频调用，保证高并发场景稳定性

### 13.2 可用性要求

- 短信供应商异常时需返回明确可重试错误
- 系统内部故障时不得产生脏会话或重复注册
- 自动注册与登录会话创建应尽量保证事务一致性

### 13.3 可观测性要求

- 接口需具备请求日志、错误日志、调用耗时监控
- 关键链路需支持 traceId/requestId 追踪
- 短信发送成功率、登录成功率、验证码错误率、刷新成功率应可统计

## 14. 边界与异常场景

- 同一手机号短时间内重复请求验证码
- 用户输入旧验证码
- 用户输入正确验证码但账号已被禁用
- 自动注册过程中数据库写入失败
- 登录成功响应发出前网络中断
- Refresh Token 已轮换，但客户端仍提交旧 Token
- 同一设备多次重复登录
- 客户端本地持有过期 Access Token 调用 `/me`

处理原则：

- 保证接口幂等性与可恢复性
- 保证状态切换可审计
- 尽量减少由于客户端重试造成的重复注册和多余会话

## 15. 开发约束与实现建议

- 后端建议按认证域拆分模块，如 `controller`、`service`、`repository`、`domain`
- 验证码服务、Token 服务、会话服务、账号服务职责要清晰分离
- 自动注册逻辑需要保证并发下同一手机号不会创建多个账号
- 可通过手机号唯一索引 + 捕获重复键异常实现并发安全兜底
- 会话状态设计需为后续“全设备登出”“设备管理”预留扩展空间

## 16. 测试与验收标准

### 16.1 功能验收

- 可以成功发送登录验证码
- 未注册手机号可通过验证码自动注册并登录
- 已注册手机号可通过验证码直接登录
- 登录成功后返回有效 Access Token 和 Refresh Token
- Access Token 可访问受保护接口
- Refresh Token 可刷新 Access Token
- 当前设备退出登录后，当前会话不可继续刷新
- 同账号多设备可同时在线，互不影响
- 被禁用或封禁账号无法登录

### 16.2 异常验收

- 错误验证码登录失败
- 过期验证码登录失败
- 已使用验证码不可再次使用
- 发送验证码频繁时接口被限流
- 刷新失效 Token 时接口返回正确错误码
- 非法 Token 访问受保护接口时被拒绝

### 16.3 安全验收

- 日志中不存在明文验证码
- 日志中不存在完整手机号和完整 Token
- 验证码与 Refresh Token 存储为不可逆摘要
- 同一 Refresh Token 轮换后旧 Token 不可复用

## 17. 二期扩展方向

以下能力建议作为后续版本演进：

- 密码设置与密码登录
- 忘记密码与找回密码
- 图形验证码
- 第三方登录
- 全设备下线
- 登录设备管理
- 异地登录提醒
- 手机号换绑
- 注销账号
- 更复杂的风控能力

## 18. 结论

本方案以“手机号验证码一体化登录注册”为核心，目标是在最短路径内完成直播 App 首版用户接入。方案兼顾移动端体验、后端实现复杂度和后续扩展空间，适合作为 V1 的认证基础设施。后续进入技术设计与开发阶段时，应以本 Spec 为基线进一步细化数据库表结构、Token 签发实现、短信供应商接入与测试方案。
